# RAID (adversarial-robustness test set for AI-image detectors)
- **Source/URL:** https://huggingface.co/datasets/aimagelab/RAID (author lab aimagelab, ungated, HF commit sha 36335df31a73..., last modified 2025-07-24; HF API https://huggingface.co/api/datasets/aimagelab/RAID) · code https://github.com/pralab/RAID · detector checkpoints https://huggingface.co/aimagelab/RAID_ckpt (not needed, do not download) · **Paper:** raid-arxiv2025 (arXiv 2506.03988; Sec 2.1-2.2 via https://arxiv.org/html/2506.03988).
- **License:** dataset card says `license: mit` (README.md header at https://huggingface.co/datasets/aimagelab/RAID/raw/main/README.md); code repo MIT (https://raw.githubusercontent.com/pralab/RAID/main/LICENSE, "Copyright (c) 2025 PRALab"). Underlying images come from ELSA D3 (https://huggingface.co/datasets/elsaEU/ELSA_D3); its HF API shows no license tag, so the upstream image/real-photo license is **[unverified]** (reals are LAION-derived web images [unverified]). Treat as research use only.
- **Size:** 96,000 images total = 24,000 originals + 3 x 24,000 attacked (paper Sec 2.1). HF file listing (tree API, per folder): each of epsilon8/16/32 holds 5 folders x 4,800 PNGs; `original/` holds 5 x 4,800 JPGs. Total on disk roughly 3 x 3.1 GB attacked + 0.9 GB originals = ~10 GB (eps8 alone ~3.15 GB: real 572.6 MB, gen_0 624.3, gen_1 673.4, gen_2 664.7, gen_3 617.1 MB; summed from listing).
- **Real sources:** 4,800 reals from D3 (folder `real`, paper Sec 2.1). **Generators (folders gen_0..gen_3):** SD v1.4, SD v2.1, SDXL, DeepFloyd IF per paper; exact gen_k-to-name mapping **[unverified]** (follows D3 order, not read from a file).
- **Formats:** attacked = PNG, 256x256 (header read by HTTP range on `epsilon8/gen_1/135830001088_gen_1_adv.png` and `epsilon8/real/135830001088_real_adv.png`), ~130-150 KB each. Originals = JPEG of varying size (our 100-id subset, checked 2026-10-24 on all 500 originals: real short side median 250 px, range 70-1444, 52 of 100 reals under 256; gen_0 exactly 256; gen_1..gen_3 about 360-512; 324x324 was only the one file first decoded, `original/real/135830001088_real.jpg`), luminance quant table starting 8,6,5,8,12,20,26,31 = standard quality ~75 table. Original JPEG sizes are small (gen_0 ~10 KB, real ~32 KB, gen_1 ~50 KB). **Pairing (verified 2026-10-24, pixel level, see experiments/010-raid-transfer/code_review.md):** the attacked PNG is the PLAIN center crop of the original JPEG to 256x256, no resize, zero-padded (black borders) when a side is under 256 (torchvision CenterCrop); max |eps8 - crop| = 9/255 and max |eps16 - crop| = 17/255 on all 500 items. So reals under 256 px carry black borders that fakes (>= 256 px) do not: a padding shortcut, handled in E3 by an unpadded primary analysis. Remaining format difference: attacked = PNG, original = JPEG q~75.
- **Layout:** `epsilon{8,16,32}/{real,gen_0..gen_3}/<id>_<cls>_adv.png` and `original/{real,gen_0..gen_3}/<id>_<cls>.jpg`. Pairing key is the numeric id (e.g. 135830001088): the id sets match for every class in epsilon8/gen_1 vs original/gen_1 (4,800/4,800). Ids are shared across classes (same id in real and gen_k; whether the gen image was prompted from the same real's caption is **[unverified]**, plausible for D3).
- **Attack ensemble (paper Sec 2.2, raid-arxiv2025):** Wang20, Corvi23, Ojha23 (UnivFD), Cavia24, Koutlis24, DRCT (CLIP and ConvNeXt backbones), L-inf PGD, 10 steps, step 0.05, ensemble mean cross-entropy. **DINOv2 / DINOv2-Reg / ViT-Tiny / CoDE are NOT in the ensemble**; they are held-out baselines (Table 4, trained as linear heads on D3). So a frozen DINOv2/DINOv3 probe is outside the ensemble (DINOv3 not mentioned in the paper). Note: RAID_IMG (the released PNGs) vs raw-tensor RAID give similar held-out numbers (Table 4: DINOv2 acc 54.8 at 16/255 RAID_IMG vs 54.6).
- **Epsilon released:** all three, 8/255, 16/255, 32/255 (folders epsilon8, epsilon16, epsilon32 exist in the HF listing). The earlier KB "mismatch" is resolved: eps 8 IS released.
- **Download procedure:** per-file HTTP GET (see Minimal subset plan). No parquet, no shards, no archives; each image is an individual file, resolve URL `https://huggingface.co/datasets/aimagelab/RAID/resolve/main/<path>` (302 to CDN; `accept-ranges: bytes`, range request returned 206 on a JPG).
- **Known issues:** (1) clean vs attacked format/size mismatch; (2) only 4 SD-family/IF generators, reals from D3; (3) all attacked images are uncompressed PNG, the worst-case no-post-processing scenario; (4) eps 16-32/255 large (paper); (5) attack surrogate is a CLIP/CNN ensemble, so transfer to DINO-type probes is weaker than to ensemble members but Table 4 shows DINOv2 still falls 83.1 -> 54.6 acc at 16/255.
- **Used in our experiments?** no (planned for idea canonicalize-vs-transfer-attack, kb/ideas/canonicalize-vs-transfer-attack.md)

## Minimal subset plan (eps 8/255 only; no sharding, so exact files can be fetched individually)
- **Files:** pick N ids from the listing (stratified); for each id fetch (a) `epsilon8/<cls>/<id>_<cls>_adv.png` for the cls assigned to it and (b) the matching `original/<cls>/<id>_<cls>.jpg`. Use 100 ids per class x 5 classes (real, gen_0..gen_3) = 500 attacked + 500 originals.
- **Sizes (from listing means):** attacked ~119-140 KB each: real 572.6 MB/4800 = 0.119 MB, gens 0.130/0.140/0.138/0.129 MB -> 500 files ~ 64 MB. Originals: real 32 KB, gen_0 10.6, gen_1 50.5, gen_2 47.1, gen_3 42.0 KB -> 500 files ~ 9 MB. **Total ~ 73 MB.** Scaling to 1,000 per set: ~146 MB; 2,000 per set: ~290 MB. Well under 1 GB and the 4 GB budget.
- **Optional second epsilon** (eps16 or 32 for comparison to paper Table 4): same ids, +~70 MB each.
- **How to sample:** build the file list from `GET https://huggingface.co/api/datasets/aimagelab/RAID/tree/main/epsilon8/<cls>?limit=1000` (paginate via Link header; 4,800 entries each; entries carry `size` and `lfs.oid` = sha256), fix seed, pick 100 ids per class from the intersection of ids present in original/ (all 4,800 match for gen_1; check others), same ids reused for attacked and original. Attacked and clean of the same id for the SAME class is the pair.
- **sha256 to record:** the `lfs.oid` in the tree listing is the file sha256; record in env/SOURCES.md for each downloaded file (verify after download) plus the HF repo commit sha 36335df31a738119b517cf77388829350fd18e9f (as seen at listing time).
- **Tooling note:** use plain `curl`/`urllib`/`huggingface_hub.hf_hub_download` per file (no full snapshot). Do not use `snapshot_download` without `allow_patterns`.
- **Clean counterpart protocol:** to compare like-for-like, decode the original JPEG and apply RAID's own preprocessing, a plain center crop to 256 with zero padding and NO resize (verified at pixel level, see Formats; the repo code itself was not read); the resulting image still carries a prior JPEG q~75 pass that the PNG attacked version may not (the attack was run on the original; whether on the 256 resampled version of the decoded JPEG is **[unverified]**).

## Blockers / unknowns
- No hard blocker: license MIT, eps 8 present, per-file fetch works, DINOv2 outside ensemble, ~73 MB for 500+500.
- **Clean/attacked mismatch [verified from headers]:** original JPEG q~75 of varying size vs 256x256 PNG. Clean "baseline AUROC" must use the same 256 center crop as RAID (not a resize); otherwise the measured "drop" mixes the attack with a different field of view (a resize control was found to differ from the attacked image by a median ~65 grey levels for 4 of 5 classes).
- The originals are already JPEG q~75, so test-time JPEG q75 canonicalisation is partly a no-op on clean data (clean cost may be ~0, which flatters the clean-cost criterion) and reals/fakes share this JPEG history only in the originals, not in the PNGs: a probe could learn "has JPEG history vs PNG" only if originals are used; avoid mixing sources across classes within one AUROC (attacked reals and attacked fakes are both PNG, which is balanced).
- Attacked reals exist (`epsilon8/real`), so AUROC (attacked fakes vs attacked reals) is computable; but note the attack drives reals toward "fake" and fakes toward "real" (target class flips, paper Eq 1-3) so both classes are perturbed adversarially.
- Reals are D3 (LAION-sourced, downscaled web images [unverified]), not camera photos; the FPR on phone photos target is not addressed by RAID.
- Generator-index mapping, caption pairing, exact preprocessing, and upstream D3 image license [all unverified].
- eps 8/255 held-out numbers are not reported in paper Table 4 (it gives 16 and 32); our eps 8 drop will be new data, can sanity-check against 16/255 (DINOv2 83.1 -> 54.6 acc).
- Design change suggested for idea #5: (1) use eps 8 and 16 (cost +70 MB); (2) add the resize-to-PNG clean control; (3) add a DINOv2 linear-head probe trained on D3-like data as a sanity anchor to Table 4; (4) pass criteria assume attack drop on B0 is measurable at eps 8, which is untested.
